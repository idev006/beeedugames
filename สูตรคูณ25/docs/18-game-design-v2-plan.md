# Game Design V2: เมืองแสงซ่อนกล — จากกลุ่มพลังสู่ความเข้าใจการคูณ

## 1. บทสรุปจากเกมเดิม

### สิ่งที่ควรรักษา

- โลกแฟนตาซีเมืองช่างพลังงานและตัวละครทีมช่าง
- ฉากมี silhouette ชัด สีสว่าง และมีพื้นที่เล่นขนาดใหญ่
- HUD แสดงหัวใจ เวลา ดาว คอมโบ และความคืบหน้า
- การเปลี่ยนเขตและ milestone เป็นแรงจูงใจที่ดี
- รองรับ Mouse, Touch และ AR ผ่านเส้นทางคำตอบเดียว
- ภาพกลุ่มพลังงานและคำอธิบายภารกิจมีฐานสำหรับต่อยอด

### ปัญหาหลักที่ต้องแก้

- ตัวเลือกตัวเลขเด่นกว่าความสัมพันธ์ของกลุ่มพลังงาน
- ภาพกลุ่มพลังงานอยู่ด้านบน แต่ไม่ได้เป็นสิ่งที่ผู้เล่นลงมือจัดการ
- gameplay หลักคือเลือกคำตอบ จึงเสี่ยงให้เด็กเดาหรือจำคำตอบโดยไม่เข้าใจที่มา
- การคูณจำนวนมากยังไม่มีเส้นทางจากภาพกลุ่มไปสู่การแยกจำนวนหรือการสลับที่
- HUD มีข้อมูลจำนวนมาก แต่ไม่ได้บอกเด็กว่าต้อง “ทำอะไร” กับกลุ่มพลังงาน

## 2. เป้าหมายการเรียนรู้ใหม่

เกมจะถือว่าเด็กเข้าใจคู่คูณหนึ่งคู่เมื่อเด็กสามารถ:

1. ระบุจำนวนกลุ่มได้
2. ระบุจำนวนในแต่ละกลุ่มได้
3. สร้างกลุ่มที่เท่ากันได้
4. เชื่อมโยงกับการบวกซ้ำได้
5. ตรวจว่าผลรวมขาดหรือเกินได้
6. แสดงภาพเดียวกันในรูปแถว/คอลัมน์และค้นพบการสลับที่ได้
7. ใช้วิธีแยกจำนวนกับโจทย์ใหญ่โดยยังย้อนกลับไปอธิบายกลุ่มเดิมได้

ความเร็วในการตอบเป็นข้อมูลเสริม ไม่ใช่หลักฐานเดียวของ mastery

## 3. Core experience ใหม่

### แบบจำลองการคูณและสมบัติการสลับที่

- ทุกภารกิจต้องสื่อ `จำนวนกลุ่ม × จำนวนในแต่ละกลุ่ม` ด้วยจุดพลังจริง ไม่ใช้เลขซ้ำเพียงอย่างเดียว
- แสดง array model สองมุมมอง เช่น 7 กลุ่ม กลุ่มละ 2 และ 2 กลุ่ม กลุ่มละ 7
- กรอบรอบคอลัมน์ทำให้เด็กเห็นขอบเขตของแต่ละกลุ่ม ส่วนจำนวนจุดทั้งหมดคงเดิม
- ก่อนตอบจะแสดงความสัมพันธ์โดยยังไม่เปิดเผยผลลัพธ์
- เมื่อตอบถูกจึงสรุป `7 × 2 = 2 × 7 = 14` เพื่อเชื่อมภาพ เหตุผล และสัญลักษณ์
- เมื่อผิดให้ชวนกลับไปนับกลุ่มและหมุนมุมมอง ไม่ใช้เพียงข้อความว่า “ผิด”

```text
พบเครื่องจักรที่ไฟดับ
  -> สำรวจว่ามีกี่แท่นและแท่นละกี่ดวง
  -> จัด/เติมพลังให้เกิดกลุ่มเท่ากัน
  -> เห็นพลังไหลทีละกลุ่มเป็นการบวกซ้ำ
  -> ตรวจคำตอบด้วยแกนพลัง
  -> หมุนหรือจัดแถวเพื่อค้นพบมุมมองใหม่
  -> เครื่องจักรทำงานและเมืองเปลี่ยนแปลง
```

Answer core ยังคงมีได้ แต่ทำหน้าที่เป็นขั้นตรวจสอบหลังเด็กสร้างความหมายแล้ว ไม่ใช่ mechanic หลักเพียงอย่างเดียว

## 4. Visual grammar

ทุกโจทย์ต้องใช้ visual grammar เดียวกัน:

- แท่น/กล่อง/รถไฟหนึ่งชิ้น = หนึ่งกลุ่ม
- พลังภายในแท่น = จำนวนต่อกลุ่ม
- กลุ่มที่ถูกต้องต้องมีจำนวนเท่ากันและมี baseline เดียวกัน
- การเติมพลังเกิดทีละกลุ่ม เพื่อทำให้เห็น repeated addition
- ตัวเลขปรากฏหลังโครงสร้างภาพเริ่มชัด ไม่ใช่ก่อนภาพ
- จำนวนมากใช้ badge, array, batch และแถบพลังแทนการวางวัตถุจำนวนมาก
- สีช่วยบอกสถานะ แต่ไม่ใช่สัญญาณคำตอบเพียงอย่างเดียว

## 5. ตัวอย่างภารกิจ `7 × 2`

### ขั้นเล่น

1. แสดงแท่นว่าง 7 แท่น
2. ให้เด็กเติมพลังแท่นละ 2 ดวง
3. พลังไหลครบทีละแท่น
4. แสดง `2 + 2 + 2 + 2 + 2 + 2 + 2 = 14`
5. แสดง `7 กลุ่ม × กลุ่มละ 2 = 14`
6. เปิดโหมดหมุนแผงเพื่อเปลี่ยนเป็น 2 แถว แถวละ 7

### หลักฐานความเข้าใจ

- เด็กจัดได้ครบ 7 กลุ่ม
- ทุกกลุ่มมี 2 ดวง
- เด็กแก้กลุ่มที่ขาด/เกินได้
- เด็กจับคู่ภาพกับ `7 × 2` และ `2 × 7` ได้

## 6. ตัวอย่างภารกิจ `25 × 12`

ไม่สร้างวัตถุ 300 ชิ้นบนจอ แต่ยังรักษาความหมายเดิม:

1. แสดงเมืองเป็น 25 แท่นในรูปแบบ 5 × 5
2. แต่ละแท่นมี badge หรือ mini-array แทน 12 ดวง
3. เปิดรายละเอียดว่า `12 = 10 + 2`
4. ให้พลังสองสายเติมแท่นเดิม:

```text
25 × 10 = 250
25 × 2  = 50
250 + 50 = 300
```

5. ให้เด็กกลับไปตรวจว่าแต่ละแท่นยังมี 12 ดวงเท่าเดิม

การแยกจำนวนเป็นเครื่องมือช่วยคิดที่เกิดจากภาพ ไม่ใช่สูตรลัดที่แยกออกจากความหมาย

## 7. โครงสร้างโหมดเกม

### Story Mission

โหมดหลักสำหรับเรียนรู้แนวคิดใหม่ มีเวลาแบบผ่อนคลายและมี hint ตามลำดับ:

```text
ชี้ให้เห็นกลุ่ม
  -> ให้เด็กลองจัดเอง
  -> แสดงการบวกซ้ำ
  -> แสดงสัญลักษณ์คูณ
```

### Mastery Repair

ทบทวนคู่คูณที่เคยผิด โดยลดบทสนทนาและเพิ่มการจัดกลุ่มซ้ำ

### Free Workshop

ไม่มีหัวใจและเวลานับถอยหลัง ให้เด็กทดลองเปลี่ยนจำนวนกลุ่ม/จำนวนต่อกลุ่ม และหมุน array

AR เป็นวิธีควบคุมที่ใช้ได้ทุกโหมด แต่ไม่เป็นเงื่อนไขของการเรียนรู้

## 8. Feedback design

เมื่อผิดต้องย้อนกลับไปหาความหมาย:

1. ชี้กลุ่มที่ขาดหรือเกิน
2. แสดงจำนวนกลุ่มและจำนวนต่อกลุ่ม
3. ให้ลองแก้กลุ่มเดิม
4. เฉลยหลังเด็กขอ hint หรือผิดซ้ำ

Feedback ต้องตอบคำถาม “ทำไม” ไม่ใช่เพียงบอกคำตอบที่ถูก

## 9. Progression

- ระยะที่ 1: แม่ 2–5, กลุ่มเล็ก, แสดงวัตถุครบ
- ระยะที่ 2: แม่ 6–10, เพิ่มแถว/คอลัมน์และการสลับที่
- ระยะที่ 3: แม่ 11–15, ใช้ batch และ visual compression
- ระยะที่ 4: แม่ 16–20, ใช้การแยกจำนวนและตัวลวงเชิงเหตุผล
- ระยะที่ 5: แม่ 21–25, ผสมหลาย representation และโจทย์จำนวนมาก

ความยากเพิ่มจาก representation และการตัดสินใจ ไม่ใช่เพิ่มความเร็วอย่างเดียว

## 10. แผนการพัฒนา

### Phase 0 — Design validation

- ทำ wireflow ของภารกิจ `7 × 2`
- ทำ visual prototype ของ `25 × 12`
- ทดลองกับเด็กหรือผู้สังเกตการณ์อย่างน้อย 3 คน
- ตรวจว่าเด็กตอบได้ว่า “มีกี่กลุ่ม กลุ่มละเท่าไร” ก่อนเห็นคำตอบ

### Phase 1 — Vertical slice ใหม่

- สร้าง mechanic จัดกลุ่ม/เติมพลัง
- ทำ feedback ขาด/เกิน
- ทำ repeated-addition animation
- ทำ answer core เป็นขั้นตรวจสอบ
- รองรับ Mouse/Touch ก่อน แล้วจึงเชื่อม AR

### Phase 2 — Representation system

- เพิ่ม array rotation
- เพิ่ม commutative discovery
- เพิ่ม batch สำหรับจำนวนมาก
- เพิ่ม decomposition ที่ย้อนกลับไปยังกลุ่มเดิมได้

### Phase 3 — Learning progression

- เพิ่ม mission data ใน JSON
- เพิ่ม mastery evidence ไม่ใช่แค่ accuracy
- เพิ่ม review queue จากคู่คูณที่เด็กผิด
- เพิ่ม Free Workshop และ Mastery Repair

### Phase 4 — Polish and validation

- playtest เด็กจริง
- accessibility และ reduced motion
- AR performance และ fallback
- ตรวจว่า reward สื่อความก้าวหน้าทางการเรียนรู้

## 11. Acceptance criteria ของเกมใหม่

- เด็กสามารถอธิบาย `7 × 2` ด้วยภาพกลุ่มได้โดยไม่พึ่งการจำ
- เด็กเห็นว่า `7 × 2` และ `2 × 7` มีผลรวมเท่ากันจากการจัด array ใหม่
- `25 × 12` แสดงแบบย่อได้โดยไม่สูญเสียความหมายของ 25 กลุ่ม กลุ่มละ 12
- คำตอบผิดครั้งแรกนำไปสู่การตรวจกลุ่ม ไม่เฉลยทันที
- ทุก input method ใช้ mechanic เดียวกันและลงท้ายที่ `GameStore.submit()`
- เกมสามารถวัดหลักฐานความเข้าใจแยกจากความเร็วได้

## 12. คำตัดสินใจ

ยังไม่ควรเพิ่ม content แม่คูณ 2–25 ต่อจากเกมเดิมทันที ควรสร้าง vertical slice ใหม่ของ `7 × 2` ให้ผ่านเกณฑ์ความเข้าใจก่อน แล้วจึงขยาย mechanic เดียวกันไปยัง `25 × 12` และแม่คูณช่วงอื่น

## 13. Engineering principles และ learner-first quality gates

### Learner-first

- ทุก mechanic ต้องมี learning purpose ที่อธิบายได้ ไม่เพิ่ม animation หรือ reward ที่ทำให้เด็กหลุดจากความสัมพันธ์ทางคณิตศาสตร์
- ต้องวัดความเข้าใจจากการจัดกลุ่ม การอธิบาย และการตรวจคำตอบ ไม่ใช้ accuracy หรือ speed เพียงอย่างเดียว
- เด็กต้องเล่นต่อได้เมื่อผิด โดยได้รับ hint ที่ช่วยสร้าง mental model ไม่ใช่แค่เปิดเฉลย
- AR, เสียง, เวลา และหัวใจเป็นตัวเสริมประสบการณ์ ห้ามเป็นเงื่อนไขที่ทำให้เด็กเข้าใจคณิตศาสตร์ได้ยากขึ้น

### Software process

- เริ่มจาก learning acceptance criteria และ wireflow ก่อนเขียน runtime code
- แยก design decision, domain rule, rendering และ input adapter ออกจากกัน
- ใช้ JSON เป็น SSOT สำหรับ mission, representation, scaffold และ progression
- ทุก feature ต้องมี unit, integration และ playtest acceptance criteria
- ทำงานเป็น vertical slice เล็ก ๆ: `7 × 2` ต้องผ่านก่อนขยายไปยังจำนวนและเขตอื่น
- ทุกการเปลี่ยน workflow ต้องอัปเดต sequence diagram และ ownership rule
- ทุก resource ที่สร้างต้องมี owner และ cleanup path ที่ตรวจสอบได้

### Maintainability และ extensibility

- ออกแบบให้การเปลี่ยน mechanic, visual representation, difficulty และ content ไม่บังคับให้แก้ scene ใหญ่ทั้งไฟล์
- ใช้ interface หรือ narrow method ระหว่าง domain, rendering, input และ feedback แทนการให้ระบบเข้าถึง internals ของกันและกัน
- เก็บกฎและข้อความที่เปลี่ยนบ่อยไว้ใน JSON/config พร้อม schema version และ validation
- แยก pure logic ที่ทดสอบง่ายออกจาก Phaser/Vue side effects
- ทุก feature ใหม่ต้องมี owner, lifecycle, cleanup path และ event contract ที่ระบุชัด
- ใช้ data-driven mission definitions เพื่อเพิ่มแม่คูณหรือรูปแบบโจทย์โดยไม่คัดลอกโค้ด
- เมื่อไฟล์ใกล้ 500 บรรทัดให้แยก module ก่อนถึง 700 บรรทัด
- รักษา backward-compatible event payload เมื่อทำได้ และเพิ่ม field ใหม่แทนการเปลี่ยนความหมายของ field เดิม
- ทุกการแก้ต้องเพิ่มหรือปรับ unit/integration test ที่ป้องกัน regression ของ workflow เดิม
- ห้าม optimize ด้วยการผูกระบบเข้าหากันจนการแก้ครั้งถัดไปกระทบ input method หรือ learning representation ทั้งหมด

### Performance engineering

- กำหนด performance budget ก่อนเพิ่ม visual complexity: ไม่สร้างวัตถุ 300 ชิ้นเพื่ออธิบาย `25 × 12`
- ใช้ visual compression, atlas และ stable scene objects เมื่อช่วยลด allocation โดยไม่ทำลายความเข้าใจ
- AR inference ต้องมี frame budget และ fallback ที่ไม่ทำให้เกมหลักหยุด
- หลีกเลี่ยง Vue updates จาก Phaser frame loop ที่ไม่จำเป็น
- วัด loading time, frame stability, input latency และ memory/object churn บนอุปกรณ์เป้าหมาย
- performance optimization ต้องไม่ลดขนาดหรือความชัดของ representation จนเด็กอธิบายที่มาของคำตอบไม่ได้

### Definition of Done สำหรับ mechanic ใหม่

mechanic จะผ่านได้เมื่อ:

1. เด็กสามารถบอกได้ว่ามีกี่กลุ่มและกลุ่มละเท่าไร
2. เด็กสร้างหรือแก้กลุ่มให้เท่ากันได้
3. เด็กเชื่อมภาพกับ repeated addition และ multiplication sentence ได้
4. มี fallback เมื่อ Mouse, Touch, AR, audio หรือ asset บางส่วนไม่พร้อม
5. ผ่าน syntax/config/lifecycle/performance checks
6. มี playtest evidence ว่าเด็กเข้าใจ action ถัดไปโดยไม่ต้องอธิบายแทนทันที

## 14. Game graphic design สำหรับเด็กประถม

งานภาพเป็นส่วนหนึ่งของ learning interface ไม่ใช่ polish ที่ทำภายหลัง เพราะเด็กต้องใช้ภาพเพื่อเข้าใจภารกิจ เลือก action และสร้างความจำระยะยาว

### Visual priorities

ลำดับความสำคัญของภาพบนหน้าจอควรเป็น:

1. วัตถุที่เด็กต้องลงมือทำ
2. ความสัมพันธ์ทางคณิตศาสตร์ เช่น จำนวนกลุ่มและจำนวนต่อกลุ่ม
3. feedback ที่บอกเหตุผลของผลลัพธ์
4. ตัวละครและ story context
5. decoration ของฉาก

ถ้าฉากสวยแต่เด็กมองไม่เห็นว่าต้องแตะอะไร ถือว่าออกแบบไม่ผ่าน

### หลักการภาพสำหรับอายุ 8–9 ปี

- silhouette ของแท่นพลัง ตัวเลือก และตัวละครต้องแยกออกจากฉากได้ในเวลาสั้น ๆ
- วัตถุ interactive ต้องมีขอบเขตและสถานะชัด: ปกติ, ชี้อยู่, กำลังล็อก, ถูก, ผิด, ถูกปิด
- ใช้ขนาด น้ำหนัก แสง และตำแหน่งช่วยนำสายตา ไม่ใช้สีเพียงอย่างเดียว
- ตัวเลขและข้อความไทยต้องอ่านได้บนมือถือและใน AR mode
- หลีกเลี่ยงฉากที่มีรายละเอียดเข้มตรง safe play area
- ใช้สีสดแบบมีโครงสร้าง ไม่ใช้เอฟเฟกต์เรืองแสงจนกลบจำนวนหรือ label
- ตัวละครต้องแสดงอารมณ์ที่ปลอดภัยและช่วยตีความสถานการณ์ ไม่ทำให้ความผิดดูน่ากลัว
- feedback ผิดต้องลดความเข้มของเอฟเฟกต์ ไม่ใช้ภาพแตก เสียงตกใจ หรือสีแดงรุนแรง
- transition ต้องสื่อการเปลี่ยนแปลงของเมืองหรือความก้าวหน้า ไม่ใช่เอฟเฟกต์ที่ทำให้เด็กเสียตำแหน่งในฉาก

### Art performance contract

- ใช้ processed runtime assets ที่มี alpha และ pivot สม่ำเสมอ
- atlas ใช้กับวัตถุที่ซ้ำกัน แต่ต้องไม่ทำให้วัตถุทางคณิตศาสตร์อ่านเล็กเกินไป
- จำกัดจำนวน particle และ animated objects ตาม device budget
- background ต้องมี safe play area ที่ตรวจสอบได้ ไม่ crop จุดโต้ตอบ
- ทุก asset ต้องผ่าน alpha, black halo, crop, frame alignment และ contrast review

### Visual playtest acceptance

ก่อนรับงานภาพหรือหน้าเกม ต้องให้เด็กหรือผู้สังเกตการณ์ตอบได้โดยไม่อธิบายแทนว่า:

1. จุดไหนคือสิ่งที่ต้องทำ
2. จุดไหนเป็นกลุ่มพลังงาน
3. ตอนนี้มีจำนวนกลุ่มและจำนวนต่อกลุ่มเท่าไร
4. ระบบกำลังบอกว่าถูก ผิด หรือกำลังรออะไร
5. หลังซ่อมสำเร็จ เมืองหรือทีมเปลี่ยนแปลงอย่างไร

ถ้าความสวยงามทำให้คำตอบของคำถามเหล่านี้ไม่ชัด ต้องลด decoration หรือปรับ hierarchy ก่อนเพิ่ม polish

## 15. Document-Driven Project operating model

โครงการนี้ใช้เอกสารเป็นตัวขับเคลื่อนการตัดสินใจ ไม่ใช่เพียงเอกสารสรุปหลังเขียนโค้ด

### เอกสารแต่ละประเภทมีหน้าที่

- Project charter: เป้าหมาย ผู้เรียน และขอบเขต
- Learning design: สิ่งที่เด็กต้องเข้าใจและหลักฐานความเข้าใจ
- Game design: core loop, mechanic, progression และ reward
- Art direction: visual language, asset contract และ readability
- Technical architecture: ownership, module boundary และ lifecycle
- Workflow sequence: ลำดับ event และ state transition
- Config/schema: กฎและ content ที่ runtime ใช้จริง
- Test plan: acceptance criteria และ regression coverage
- ADR: เหตุผลของ technical decision ที่มีผลระยะยาว

### Change workflow

```text
พบปัญหาหรือข้อเสนอ
  -> ระบุผลกระทบต่อผู้เรียนและ scope
  -> แก้เอกสาร source of truth
  -> ระบุ acceptance criteria และ test case
  -> implement ตาม contract
  -> ตรวจ runtime และ playtest
  -> อัปเดต workflow/architecture/changelog
```

### Definition of Ready

งานใหม่จะเริ่ม implement ได้เมื่อมี:

- เป้าหมายการเรียนรู้ที่ชัด
- ภาพหรือ interaction ที่ต้องการสื่อ
- owner และ module boundary
- config/schema ที่เกี่ยวข้อง
- acceptance criteria
- ผลกระทบต่อ workflow และเอกสารที่ต้องอัปเดต

### Definition of Done

งานจะถือว่าเสร็จเมื่อ:

- โค้ดสอดคล้องกับเอกสารล่าสุด
- ผ่าน syntax, config, lifecycle และ performance checks
- มีการทดสอบตาม acceptance criteria
- ผู้เรียนยังเข้าใจที่มาของคำตอบได้
- ไม่มี stale event, stale timer หรือ resource leak ที่เกี่ยวข้อง
- เอกสาร workflow, architecture และ version ถูกอัปเดตแล้ว
